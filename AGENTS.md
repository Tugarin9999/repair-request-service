# AGENTS.md

Сервис приёма заявок на ремонт для небольшой ремонтной мастерской. Каркас, слой данных, оба экрана и тесты готовы.

## Источник истины

`TZ.txt` — это требования (на русском, UTF-8 без BOM, CRLF). Это единственный документ проекта. Читай его до любого проектирования; доменные правила ниже извлечены из него и не являются деталями реализации, которые можно менять.

## Стек — решён, а не предложение

Python + Streamlit + SQLite. Не подменяй на FastAPI/Flask/Postgres/React без прямого указания, даже в `TZ.txt` это сформулировано как «Рекомендуемый стек» — подтверждено, что это обязательное требование.

Весь пользовательский текст и доменные значения — **на русском**. В частности, конвейер статусов — это фиксированная последовательность литеральных русских строк именно в таком порядке:

```
принято → диагностика → ремонт → готово → выдано
```

Определи их один раз в отдельном модуле с enum/константами и переиспользуй. Не хардкодь слова в ветках UI, не переводи их на английский, не придумывай дополнительных статусов и не пропускай состояния — порядок и есть продукт.

## Доменные правила, которые легко сделать неправильно

- **Номер заявки уникален и является единственным ключом поиска для клиента.** Клиент должен получать текущий статус по одному только номеру.
- **Статус меняется только у существующей заявки.** Защищай путь записи; отсутствующий номер не должен ничего вставлять или изменять.
- **Неизвестный номер должен давать понятное, дружелюбное сообщение** — не стектрейс, не пустой результат и не «not found» языком разработчика.
- **Клиентский экран статуса никогда не должен показывать контактные данные.** Контакты есть в заявке, но они нужны только мастерской. Это явный критерий приёмки, и он легко утекает, если одну и ту же строку/колонку переиспользовать для обоих экранов.
- Две роли — два экрана: клиент (подать заявку и проверить статус) и мастер (список заявок и смена статусов). Не объединяй их в один экран.

## Структура проекта

- `app.py` — единственная точка входа Streamlit. Вызывает `init_db()` и разводит роли в боковой панели, отдавая ровно одному из двух экранов; экраны намеренно не сливаются в один.
- `repair_service/statuses.py` — единственный источник статусов (`Status`, `PIPELINE`, `INITIAL_STATUS`). Нигде больше статусы не объявляются.
- `repair_service/config.py` — пути и тексты. Каталог данных переопределяется переменной `REPAIR_SERVICE_DATA_DIR` (нужно для изолированных тестовых БД).
- `repair_service/models.py` — `Request` (полная заявка, только для мастера) и `RequestStatusView` (только номер, статус, комментарий, дата).
- `repair_service/db.py` — `connect()`, контекстный менеджер `session()` (транзакция + гарантированное закрытие) и `init_db()`. Схема применяется идемпотентно, миграций нет.
- `repair_service/repository.py` — доступ к данным: `create_request`, `get_request_for_client`, `get_request_for_master`, `list_requests`, `update_status`, `update_comment`, `normalize_number`.
- `repair_service/auth.py` — пароль экрана мастера. Живёт только в переменной окружения `REPAIR_SERVICE_MASTER_PASSWORD`, нигде не сохраняется; сравнение постоянного времени по байтам UTF-8.
- `repair_service/views/client.py` — экран клиента: форма заявки и проверка статуса. Контакты сюда не выводятся ни при каких условиях.
- `repair_service/views/master.py` — экран мастера: вход по паролю, список заявок и смена статусов. Единственное место, где видны контакты; статус выбирается только из `PIPELINE`.
- `data/requests.db` — база, в git не отслеживается.
- `requirements.txt` — только runtime (`streamlit`). `requirements-dev.txt` подтягивает его и добавляет `pytest`. Всё остальное ставится в `.venv` одной командой.
- `tests/test_data.py` — 21 проверка слоя данных по критериям приёмки.
- `tests/test_auth.py` — 6 проверок пароля, без зависимостей.
- `tests/test_app.py` — 13 проверок экранов через `streamlit.testing.v1.AppTest`; нужен установленный streamlit, поэтому живёт только в `.venv`.

## Проверка и запуск

Окружение — `.venv` в корне, в git не отслеживается. Ставится один раз:

```
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Тесты (каждый тест поднимает свою временную БД через `REPAIR_SERVICE_DATA_DIR`, основная база не страдает):

```
.venv\Scripts\python.exe -m pytest -q
```

40 проверок: 21 на слой данных, 6 на пароль и 13 на экраны. Слой данных и пароль запускаются вообще без зависимостей, если venv нет: `python tests\test_data.py` и `python tests\test_auth.py`. Экраны проверены через `streamlit.testing.v1.AppTest` — это прогон настоящего `app.py` без браузера, поэтому проверяется не вёрстка, а поведение: `app.exception` после каждого действия обязан быть пустым.

Приложение. Пароль мастера обязателен: без `REPAIR_SERVICE_MASTER_PASSWORD` экран мастера закрыт, а не открыт с пустым паролем.

```
.venv\Scripts\python.exe -m streamlit run app.py
```

Одна строка PowerShell с паролем:

```
$env:REPAIR_SERVICE_MASTER_PASSWORD = "мастер-2026"; .venv\Scripts\python.exe -m streamlit run app.py
```

## Пароль мастера: чего он не делает

У Streamlit нет серверного слоя сессий, поэтому пароль — шлюз в интерфейсе, а не настоящая аутентификация. Он закрывает список заявок и контакты от того, кто просто открыл приложение, но **не** защищает файл базы и **не** защищает трафик: по обычному HTTP пароль уходит открытым текстом. На общей сети клиентов этого достаточно, для выхода в интернет — нет. Не называй это аутентификацией в требованиях к продукту.

Проверено на Python 3.14.2: streamlit 1.64.0, pytest 9.1.1, sqlite3 3.50.4, `/_stcore/health` отвечает `200`.

## Грабли, которые уже наступили

- **`StrEnum`-члены равны своим строкам.** Поэтому проверка `status not in PIPELINE` пропускала обычную строку `"принято"` мимо. Теперь `_require_pipeline_status` проверяет `isinstance(status, Status)` явно. Не полагайся на сравнение значения с членом enum как на проверку типа.
- **Кириллица в сравнениях NFC против NFD.** Две строки в тесте выглядели одинаково — `Ждёт` (`D0 91`) и `Ждём` (`D0 B5 D1 82`) — и это были разные строки. Streamlit при этом ничего не нормализует: и NFC, и NFD проходят виджет, форму и SQLite байт в байт (проверено отдельно). Значит расхождение всегда в твоих собственных литералах. Не набирай кириллический литерал дважды — бери одну константу, иначе тест падает на пустом месте.
- **`datetime` нельзя отдавать в sqlite3 напрямую** — адаптер deprecated с Python 3.12. Моменты времени форматируются явно через `_stamp`, разбираются через `_parse_time`. Проверяй с pytest `-W error::DeprecationWarning`.
- **`db.config.DATA_DIR_ENV` вместо `DB_PATH`:** путь к базе вычисляется в момент вызова, иначе подмена переменной окружения не действует после импорта.
- **`hmac.compare_digest` не работает с не-ASCII строками** — кириллический пароль ронял `verify()` с `TypeError`. Сравнивать надо байты UTF-8. В проекте с русским паролем это не крайний случай, а ожидаемый.

## Слой данных: решения, которые не видны из сигнатур

- **Контакт не может утечь к клиенту на уровне типов.** `get_request_for_client` возвращает `RequestStatusView`, где полей `contact` и `fault` физически нет. Не переиспользуй `Request` для клиентского экрана «чтобы показать побольше» — это единственный критерий приёмки, который ломается тихо.
- **Номер заявки: `ГГГГ-0000`**, сквозной в пределах года, начиная с 0001. Уникальность обеспечена первичным ключом, а не соглашением; при коллизии вставка повторяется, а не падает.
- **`normalize_number` прощает ввод**: `2026-1`, пробелы и регистр приводятся к `2026-0001`; не-номер даёт `None`. Клиент диктует номер голосом, поэтому строгий парсер здесь —UX-ошибка.
- **Защита пути записи — это сам SQL**, а не проверка в коде: `UPDATE ... WHERE number = ?` и возврат `cursor.rowcount > 0`. Несуществующий номер не может ничего вставить или изменить.
- **`update_status` отклоняет статус вне `PIPELINE`** через `ValueError`. Это единственная точка, где конвейер реально защищён от подмены.
- **Значения статусов в БД — русские строки без перевода.** Чтение мусора (`'ACCEPTED'`, `'принято '`, `''`) поднимает `ValueError` из `Status.from_value` — это осознанно: лучше упасть, чем показать клиенту выдуманный статус. Не оборачивай это в тихое значение по умолчанию.
- **Список для мастера отсортирован по номеру**, то есть хронологически и по возрастанию: старые заявки первыми, как очередь.

Известный пробел, не покрытый требованиями: логина как такового нет, только один общий пароль мастерской. `TZ.txt` про вход не говорит, поэтому решение принято по твоей просьбе; если появятся несколько мастеров, понадобится отдельная история.

## Данные (из требований)

Заявка: номер, устройство, неисправность, контакт, статус, комментарий, даты (во множественном числе — в требованиях не уточнено, какие именно; `created_at` + `updated_at` — разумное прочтение, уточни, если это важно).

## Особенности окружения на этой машине

- **Консоль в cp866.** Кириллический вывод нативных команд возвращается мусором (`��`). Это артефакт отображения, а не испорченные файлы — не «чини» кодировку из-за него. Если реально нужно прочитать кириллицу, сначала выполни `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`.
- **Сам путь репозитория кириллический** (`Сервис приёма заявок на ремонт`). Бери пути в кавычки; некоторые инструменты не справляются с не-ASCII путями.
- **Идентификация git не настроена** (нет глобальных `user.name`/`user.email`), поэтому коммиты падают, пока не задана идентичность. Не настраивай её без явной просьбы.
- **Первый запуск Streamlit спрашивает email в консоли** и блокирует неинтерактивный старт. Отключено через `%USERPROFILE%\.streamlit\config.toml`: секция `[server]`, ключ `showEmailPrompt = false`. Файл **без BOM** — парсер `toml` падает с «Found invalid character in key name», а `Set-Content -Encoding UTF8` в PowerShell 5.1 BOM добавляет. Пиши через `[System.IO.File]::WriteAllText($p, $c, (New-Object System.Text.UTF8Encoding($false)))`.
- В stderr фонового процесса Streamlit сыпет `UnicodeEncodeError` на `⚠` — это его фича «one-click skills install» (симлинки не поддерживаются, консоль в cp1251). К приложению отношения не имеет, не чини.
- Python 3.14.2 доступен и как `python`, и как `py`. Модуль `sqlite3` из стандартной библиотеки присутствует (3.50.4).
- **Линтера и CI нет** — решение не принято. Стиль держать тем же, что в существующих модулях: типизация, `from __future__` не нужен, порядок функций «приватные внизу».
- `requirements.txt` пинит `streamlit==1.64.0`, `requirements-dev.txt` подтягивает его через `-r` и добавляет `pytest==9.1.1`. Оба пина проверены на Python 3.14.2: всё ставится wheels, сборки из исходников нет.
